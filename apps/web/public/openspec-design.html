Spec 与 Issue 的独立关联

技术设计示例 · OpenSpec

Context背景

一份 Spec 往往拆成多张 Issue，同一项基础工作也可能支撑两份 Spec。团队成员从网页维护关联，Agent 从 MCP 操作。两者可能同时发出请求，也可能对关联两端拥有不同的访问权限。

Goals / Non-Goals目标与非目标

目标
允许成员从任一端找到有权查看的关联记录。重复建立同一关联时，两端都只显示一次。
非目标
本次设计只管理关联关系。Spec 的修订与 Issue 的状态流转各自独立。

Decisions设计决定

01　单独保存关联关系

每条关联记录保存一对 Spec ID 和 Issue ID。给 Issue 添加单个 Spec ID 更简单，但任务支持第二份规格时就得覆盖原值或复制任务。独立关联表支持多对多，解除关联也只需删除这一对记录。

02　由数据库保证同一对记录只关联一次

网页和 Agent 可能同时查到“尚未关联”。在两个 ID 上建立联合唯一约束，并把重复写入处理为成功，让调用方可以安全重试。

查看时序图 · 两个调用方同时建立关联

03　对关联两端分别检查权限

能看到 Spec 的人未必能看到私有团队的 Issue。网页和 MCP 共用业务层的权限判断。读取时只返回双方都可见的记录，写入时先校验两端的操作权限。

Risks / Trade-offs风险与取舍

计数可能泄露私有任务
关联列表和数量使用相同的可见性条件。因此，两位成员打开同一份 Spec 时，可能看到不同的计数。
双向查询多一次联表
按 Spec 查看任务和按 Issue 回查规格是两条主要查询路径。分别验证查询计划，为反向查询补上合适的索引。
